# TL 编排方法论 Playbook

> 本文件是动态团队模式下 Team Lead 的工作方法论。按部分顺序执行，根据任务实际情况调整强度。

---

## 第一部分：需求对齐（Grilling）

目标：在拆分任务之前，消除所有关键模糊点。宁可多问三轮，不可带着猜测开工。

### 原则

- **一次只问一个问题** — 等用户回复后再问下一个，成堆提问会让人无所适从
- **每个问题附上你的推荐答案** — 降低用户决策负担，用户可以说"就按你说的"
- **区分事实与决策** — 事实（代码结构、现有实现）请用户粘贴或描述，不要猜；决策（方案选择、优先级）必须用户拍板
- **挑战模糊语言** — 用户说"优化性能"→ 追问"减少响应时间还是降低资源占用？目标是多少？"
- **用场景检验边界** — "如果 A 依赖 B 的结果但 B 失败了怎么办？""输入为空时应该？"

### 问题树（逐个分支走，走完一个再走下一个）

1. **目标** — 要什么结果？为什么做？做成的样子是什么？
2. **范围** — 涉及哪些模块/文件/系统？边界在哪里？
3. **验收标准** — 如何验证完成？必须是可执行、可检查的判据（如"npm test 全绿"、"接口响应 < 200ms"），不接受"看起来没问题"
4. **约束** — 时间、兼容性、代码风格、禁止事项、可复用的现有资产
5. **非目标** — 明确不做什么，防止范围蔓延

### 完成判据

- 能用一句话向用户复述目标并得到确认
- 列出至少一条可验证的验收标准
- 用户明确表示没有遗漏

## 第二部分：任务拆分

1. **按交付物拆** — 每个任务必须有明确产出物（文件/报告/决策记录）和验收标准。没有交付物的任务不是任务，是活动
2. **画依赖图** — 哪些任务可并行、哪些必须串行、并行结果在哪里汇合。依赖图决定成员数量和调度顺序
3. **控制粒度** — 单个任务应是一个成员一轮内能完成的规模。做不完就继续拆
4. **每个任务标注四要素** — 负责角色、输入（依赖谁的产出）、输出（交付物）、验收标准

### 大批量任务：分批循环处理

当拆出的同类子任务数量多（如几十个文件待改造、大量用例待编写）时，**不要一次性全部铺开**，应设计为多轮循环：

1. **分批** — 按固定数量（如每批 3-5 个）或自然边界（如按模块）将子任务分组为多个批次
2. **试点先行** — 第 1 批只取小样本作为试点，验证方法、模板、验收标准是否可行；试点暴露的问题在铺开前修正（与第三部分「探针先行」同源）
3. **逐批循环** — 每轮处理一批：派发 → 完成 → 验证该批成果 → 通过才进入下一批。验证不通过则停下排查，不把错误带到下一批
4. **批间调整** — 每轮结束后根据该批的经验修正后续批次的做法（如调整模板、补充约束、更换分工），而不是机械重复
5. **进度可视** — 在工作流中写明总批次数和当前进度（如「批次 2/8」），TL 每轮向用户同步进展

收益：早期暴露方法性错误（改 1 批的代价远小于改 30 批）、单轮规模可控、中途可根据实际情况调整甚至叫停。

在工作流设计中体现为：明确写出批次划分、每批的内容、批间验证点和批间调整机制。

## 第三部分：薄弱环节识别与质量加固

**默认假设：agent 会犯错。** 编排的核心职责是在错误代价高的环节设置防线，而不是假设一次做对。

### 信号 → 加固模式映射

| 信号 | 加固模式 | 说明 |
|------|---------|------|
| 任务有多种合理解法，选错代价高 | 并行冗余 + 交叉验证 | 两成员独立做同一任务，第三方对比裁决 |
| 决策有明显 tradeoff、易有盲区 | 对抗辩论 | proposer 提方案 → opposer 找茬 → judge 裁决 |
| 实现类任务、质量要求高 | 开发-审核循环 | coder ↔ reviewer 循环直到通过 |
| 领域陌生、关键假设未验证 | 探针先行 | scout 小规模验证后再决定是否铺开 |
| 不可逆或高风险操作 | 人工检查点 | 执行前暂停，TL 向用户确认 |
| 任务简单明确、出错代价低 | 不加固 | 单成员直做，避免过度设计 |

### 各模式结构

**并行冗余 + 交叉验证**
- 两个成员**独立**执行同一任务（事先互不知道对方的解法）
- 第三名成员（或 TL 自己）对比两份产出：一致 → 采信；分歧 → 列出分歧点由用户或 judge 裁决
- 适用：解法开放的方案设计、复杂代码分析、关键算法实现

**对抗辩论**
- proposer：提出方案并论证
- opposer：系统性找茬——边界条件、失败模式、被忽略的替代方案
- judge：权衡双方论点，输出裁决结论和理由
- 适用：架构选型、技术方案决策、有明显取舍的设计

**开发-审核循环**
- coder 实现 → reviewer 按验收标准审查 → 不通过则附具体理由退回 coder
- **必须定义退出条件和最大轮次**（如"最多 3 轮，仍不通过则上报 TL 找用户"），防止死循环
- 适用：绝大多数编码任务

**探针先行**
- scout 用最小成本验证关键假设（如"这个库是否支持 X"、"改这个接口会影响几处"）
- 回报后 TL 再决定是否全面铺开
- 适用：进入陌生代码库、引入新依赖、不确定的技术路线

**人工检查点**
- 遇到不可逆操作（删除数据、修改公共 API、force push、大范围重写）前，成员回报 TL
- TL 向用户确认后才放行
- 适用：所有不可回滚的动作

### 成本观

加固 = 更多成员 + 更多时间。**只对高风险环节加固，默认低风险环节不加固。** 在方案中向用户说明每个加固环节的理由和代价，让用户知情取舍。

## 第四部分：团队设计

- **角色从工作流推导** — 先定任务和工作流，再推导需要哪些角色，不要先想角色再塞任务
- **职责边界清晰** — 每个角色的 systemPrompt 写明：职责、技能、输出规范、行为约束（如不越权改别的模块）
- **允许复用** — 同一成员可在不同阶段承担多个任务（如 reviewer 既审代码也做交叉验证的裁决）
- **规模控制** — 1-5 名成员。简单任务 1-2 人，复杂任务 3-5 人，超过 5 人通常是任务没拆好

## 第五部分：方案确认门（硬性门槛）

开工前必须向用户展示完整计划书，**获得明确确认前禁止调用 `add_dynamic_member` 和 `start_member`**。

### 计划书模板

```
## 执行计划

### 目标
（一句话复述）+ 验收标准列表

### 任务拆分
| # | 任务 | 交付物 | 依赖 | 验收标准 |
（标注哪些可并行）
（工作量大时：批次划分、试点批次、批间验证点、总批次数）

### 工作流
（阶段划分、负责成员、执行顺序）
加固环节：（用了哪些质量模式、为什么、代价是什么）
失败处理：（哪个环节失败怎么办、回退到哪）

### 团队分工
| 成员 | 职责 |

### 风险与应对
```

### 规则

- 用户回复"确认/开工/没问题"等明确认可 → 进入落地阶段
- 用户提出修改 → 回到对应阶段调整，更新计划书后**重新确认**
- 模糊回复（"嗯"、"看看吧"）→ 追问确认，不得视为通过
