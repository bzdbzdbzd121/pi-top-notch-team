# ADR-0009: 动态 / 自主团队命名 —— 一个名字、设计期改名窗口、命名是建议

## 状态

已接受（实现已交付：阶段 1–6）

## 背景

动态团队（`/team dynamic`）与 agent 自主会话（`start_team_session`）此前一律使用系统兜底名 `_dynamic_<ts>`：状态栏、`/team status`、`/team resume` 与成员提示词里看到的都是时间戳，用户无法辨认"这是哪个团队"。需求是让团队可以在开工前拥有一个可读的名字。

方案形成期确认了四个容易做错的点：

1. 名字是否同时决定 `sessions/` 目录名（"一个名字"还是"显示名 + 存储键"）？
2. 什么时候允许改名？成员进程启动时有哪些东西被固化？
3. 命名是硬门控（不命名不许开工）还是建议？
4. 未命名如何判定——要不要新增状态字段？

本 ADR 记录三个**高逆向成本**或**外人会意外**的裁决，以及被否决的替代方案与切换条件。完整的实现细节（改名事务 14 个编号步骤——即 `src/session/rename-team.ts` 的 Step 1-14，其中 8-10 为目录搬迁一组——、stub 判定、resume 自愈、UI/提示词接线）见 DESIGN.md §36。

## 决定

### 1. 一个名字：用户可见名 = 清单名 = `TEAM_NAME`，目录名随之一致（但这不是需求）

- `TeamDefinition.name` 保持唯一权威；不新增 `displayName`，不新增清单字段，`manifest.version` 不变。
- 会话目录 = `sessions/<团队名>/<sessionId>/`。改名时整棵 `<sessionId>` 子树一次原子 `rename` 到新名字的父目录，旧父目录若空则清理。
- 用户明确说过"不在意 `sessions/` 下的目录名"。这不改变结论：如果引入第二套"存储键"，就必须把"会话种类 / 存储键"作为新参数穿到每一处路径派生（共享上下文、成员会话目录、清单、resume 定位、临时设置绑定、启动建目录）以及两个只拿到 `teamName` 与 `sessionId` 的纯提示词构建函数——漏传一处的后果是"清单在 A、成员目录在 B"的静默分裂，比一次受限窗口内的目录改名更长期、更隐蔽。
- 未命名 = 名字仍是系统兜底名 `_dynamic_<ts>`。因为命名规则要求"首字符必须是字母或数字"，用户不可能构造出 `_dynamic_*`，所以"是否未命名"可以**可靠推导**，不需要新增状态字段。

**后果**：改名必须是"一次目录搬迁 + 一串幂等收尾"的事务；`/team resume` 以**目录名**为权威团队名（清单写入丢失时自愈），而不是盲信清单里的 `teamName`。

### 2. 改名窗口 = 设计阶段（∧ 无成员进程在跑，后者是防御纵深）

允许改名的判据是四条的合取：会话活跃 ∧ 动态会话 ∧ `dynamicPhase === "design"` ∧ 没有任何成员进程处于 running（最后一条是防御纵深）。

理由不是"目录搬家麻烦"，而是**成员侧在 spawn 时固化**了四样东西：环境变量 `TEAM_NAME`（成员提示词里"你是团队 X 的成员"）、绝对路径 `TEAM_SHARED_CONTEXT_PATH`、`--session-dir <绝对路径>`、以及已下发的成员系统提示词文本。启动后再改名，老成员会自述旧名、共享上下文路径失效——**即使改走"只改显示名、不搬目录"的路线，这个问题同样存在**，不一致只是从磁盘目录转移到成员自述。

因此**第一个成员成功启动后名字冻结**：`set_team_name` 仍可调用（执行阶段白名单刻意放行），但会被工具以"执行阶段/名称已冻结"的理由拒绝，并给出真实出路（结束会话后重开、在启动成员前命名）。注册成员（`add_dynamic_member`）**不是**冻结点：它只改内存名册，不影响任何成员进程。

**后果**：命名必须发生在**第一次成功的 `start_member`** 之前；提示词与工具文案统一以"启动成员"为冻结点。

**崩溃 / 主动停止的成员不会重新打开窗口。** 阶段在第一个成员**成功启动**时翻为 `execution`（`onDynamicPhaseTransition`）并写入清单，`/team resume` 也从清单恢复该阶段；`applyTeamName` 在校验顺序上**先判 `dynamicPhase !== "design"`（返回 `phase-execution`）再判是否有 running 进程**，所以"成员后来崩了/被 stop 了"仍然拒绝改名——窗口不会因成员进程消失而回退。

**唯一不被阻断的"成员相关"失败**是：`start_member` **启动失败**（进程未成功启动、阶段未翻转）。此时设计阶段仍在，即使残留了非 running 的 handle，防御检查也不触发，改名照常成功（残留成员目录随会话子树一起搬迁）。

代码/测试锚点：`src/session/rename-team.ts` 的步骤 1-4（第 3 步阶段判定先于第 4 步 running 判定）；`src/session/rename-team.test.ts` 的「执行阶段（phase-execution）」用例；`src/tools/team-name-tool.test.ts` 的「start_member 失败残留 handle（非 running）之后仍可改名」用例。

### 3. 命名是建议，不做硬门控

`start_member` 已经有一道硬门（未写共享上下文则拒绝）。再加一道"必须先命名"会让同一动作有两个前置条件、错误互相遮挡（仓库记录过"协议步骤互相锁死"的教训），而命名失败的后果只是"名字不好看"，与共享上下文（成员上下文一致性）不在同一量级。agent 入口的名字本来就是可选参数，硬门控也无法覆盖它。

**后果**：`start_team_session({teamName})` 合法则直接用，非法/撞名/缺省一律用兜底名开会并在结果里说明原因（任务委派优先，绝不因命名失败拒绝开会）；动态入口通过一次性提醒（首个成员注册时）与提示词建议引导，不拦截任何动作。提示词中不得出现"不命名会被拦截"这类假话。

## 被否决的替代方案与切换条件

- **方案 B：只加显示名（`displayName`），身份名与目录继续用 `_dynamic_<ts>`。** 优点：零路径风险，任意时刻可改名。否决：同一团队两个名字（`TEAM_NAME` 用哪个都不对）；执行阶段"改名"只是界面变、运行中成员不变；长期维护两套名字语义。**切换条件**：若将来确需"执行阶段改名"，这是唯一有意义的路线，额外必做项 = `TEAM_NAME` 改用显示名 + 残留识别改用会话 ID + `/team resume` 双字段匹配 + 接受"老成员自述滞后"。
- **方案 C′：动态会话固定父目录（`sessions/_dynamic/<sessionId>/`），名字只作元数据，改名不搬目录。** 否决：需要把"存储键"穿进每一处路径派生（见决定 1 的论证），且会长期存在两套存储布局。**变体更危险**：改名不搬目录但在清单里持久化"目录名"字段——名字与目录名从"恒等"变成"需查清单"，任何仍直接读 `team.name` 的旧代码都会静默算错。
- **方案 F：从任务文本自动派生名字。** 否决：仓库既有 slug 只保留 ASCII，中文任务会退化成 `team`；且与"让 TL 指定"的诉求相反。
- **方案 D：只加 `start_team_session` 名字参数，不做改名工具。** 否决：`/team dynamic` 下 TL 在会话创建之后才存在，不给改名能力就无法命名。
- **方案 G：命名做成硬门控。** 否决见决定 3。
- **方案 H：命令层输入框或 `/team dynamic <名字>` 参数。** 否决：输入框在 RPC / 无 UI 环境不可用；**用户明确确认不需要 `/team dynamic <名字>` 参数**（多余参数继续被忽略，与今天一致）。

## 后果与已知限制

- **无数据迁移**：不新增清单字段、不升 `manifest.version`；旧 `_dynamic_*` 会话按"未命名"处理（状态栏显示「未命名团队」），恢复路径不变。
- **显示**：状态栏标题对兜底名显示「未命名团队」；`/team status` 与 `/team resume` 仍显示真实名字（便于排查与定位）。名字上限 20 显示列（中文按 2 列），与状态栏标题预算 `min(20, 宽度/4)` 对齐。
- **共享上下文**：改名只在文件仍是"系统生成的 stub"（结构化判定：旧名标题 + 自动创建警示 + 未改动的占位章节；仅成员名册块允许变化）时用新名重写；TL 写过的内容逐字节不动，只附注"请重新 `write_shared_context`"。判定结果以 `rewritten / not-stub / missing / undecidable / write-failed` 如实返回，不虚构原因。
- **已知限制**：执行阶段不能改名（见决定 2）；`/team delete` 仍只以 YAML 团队定义为入口，不清理动态会话目录（既有行为，本方案不改）；提示词建议只是引导，不能保证模型一定命名。
